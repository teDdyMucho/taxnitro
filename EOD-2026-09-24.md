EOD: TaxNitro – rebuilt four admin screens to the new design, then went back and found what I had broken doing it

1. Rebuilt the admin dashboard, the clients list, a client's folders, and the documents screen to Camaree's design.
2. Dashboard: one row of cards instead of two, a clients-by-service chart with a tooltip on hover, and recent uploads split into two columns that page five at a time.
3. Clients: a grid of cards instead of a long list, with the services down the left as filter blocks.
4. A client's folders are drawn as folders now, in a grid, with TAX / BK / CFO tabs above them. All three tabs show whether the client is on that service or not, because an empty tab is where their folders will appear if they are added to it.
5. Documents: a card per client showing how many files of theirs are waiting, split into Unsorted and Sorted, and View / Accept / Reject spelled out on each row rather than a tick and a cross.
6. The design's four service cards are three. There is no YER in this system — the database rejects it — and adding one is a service, not a screen.
7. Same for company names, client logos and the three-way client status: none of them existed, so the cards use what we do hold.
8. Then Angelo asked me to check whether I had broken anything. I had.
9. The search box on the documents screen was gone, but three filters still read from it. Staff had no way to search for a client there at all. Put it back.
10. The folder-filter dropdown was still rendered and could no longer be opened by anything. Deleted it — the tabs replaced it.
11. The view-cycle button showed the view you were in rather than the one it would take you to, which is the opposite of what it used to do.
12. Backing out of a folder landed on the wrong service tab, so the folder you had just been in was not on screen. It follows the folder now.
13. Went looking for the worst kind of mistake: I had added uploaded_by_role to the query across all twenty folder tables, and a table missing that column returns an error, which would have silently dropped every document in it from every count on the dashboard. Checked — one migration covers ten tables, another covers all twenty. Safe.
14. Added an account_status column: active, paused, closed. is_active is a boolean and cannot tell a pause from a cancellation.
15. A trigger keeps is_active and the status in step, so the staff page's deactivate button still works without knowing the column exists.
16. Angelo confirmed the meanings from Paul's note: paused is a subscription paused or delayed, closed is cancelled or no longer provided.
17. Clients switched off today become paused rather than closed. A wrong guess at paused is recoverable; marking a live client as gone is not.
18. The manage tray offers all three now. Before that it only had on and off, so "Closed" would have read zero forever.

I broke four working things and only found them because Angelo asked. Each was a control I removed while moving things around, and each left behind state or a modal that nothing could reach any more. The typecheck was clean through all of it — none of these are type errors.

database/profiles_account_status.sql is written but has not been run anywhere. Docker was down all day so I could not test it against a real Postgres. Worth running it somewhere that is not production first: it adds a column, backfills, adds a trigger, and replaces a function that also lives in profiles_client_editable.sql.

One thing I cannot test from here: the gear and documents buttons on a client card now sit inside a card that is itself pressable. On React Native that is fine, but on web both can fire, so pressing the gear may also open the progress panel behind it. Needs a click in a browser.
